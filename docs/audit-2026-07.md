## 1. Блокери публікації (PLY)

### PLY-9 · Критично · Play Console не створений — це і є критичний шлях

Перевірено у відкритих джерелах (липень 2026):

- Персональний акаунт розробника, створений після 13.11.2023, зобов'язаний провести **закритий тест: ≥12 тестувальників, opted-in 14 днів безперервно**, і лише потім подавати заявку на production access.
- Акаунти-організації (зареєстрована юридична особа) **звільнені** від цієї вимоги, але для них потрібен **D-U-N-S номер**, отримання якого може займати 30+ днів.
- Верифікація особи для персонального акаунта: від кількох годин до 2 робочих днів.
- Заявка на production access: огляд «зазвичай до 7 днів». Далі ще огляд самого релізу — до 7 днів.
- Реалістичний end-to-end для нового персонального акаунта, за оцінками практиків: **3–5+ тижнів**.

**Наслідок:** публікація в production у середині серпня з нуля недосяжна для персонального акаунта. Детальний перерахунок дати — `docs/release-plan-google-play.md` §0. Правила Google змінюються — **перевір у самій Play Console**, а не за цим документом.

### PLY-1 · Критично · Немає видалення акаунта (складніше через спільні аркуші)

Grep по `deleteUser` / `deleteAccount` / `currentUser.delete` — нічого. При цьому застосунок дозволяє створення акаунта (Firebase Auth + Google Sign-In), тобто Play вимагає видалення **в застосунку** плюс **веб-URL** для запиту.

Через кілька редакторів наївний каскад знищить дані інших людей. Правильна логіка (owner/editor, передача ownership) і чому потрібна Cloud Function — у `docs/collaborative-editing.md` COL-10. Плюс правило: зараз `users` має `allow delete: if false`.

Файли: `src/screens/Settings/Settings.tsx`, `src/shared/components/Firebase/Auth.tsx`, `firestore.rules`, новий `src/services/accountDeletion.ts` + серверна функція.

### PLY-2 · Критично · Немає Privacy Policy — ✅ Виправлено 2026-08-12

Жодного згадування в коді, i18n чи `app.json`. Обов'язкове поле в Play Console. Через спільне редагування текст має додатково розкривати, що **вміст аркуша стає видимим запрошеним співредакторам** і що DM бачить журнал змін гравця — це передача даних між користувачами, і її треба задекларувати в Data Safety.

**Перевірено 2026-08-12 (живий сайт, не з чужих слів):** `https://www.mythgatednd.pp.ua/privacy` — повний текст (розкриття видимості аркуша співредакторам і DM присутнє), обидві мови через кнопку «EN», секція видалення акаунта на тій самій сторінці (`id="account-deletion"`). Лінк у застосунку оновлено на цей URL (`Settings.tsx:22`). Поле в самій Play Console — не перевірено (дія в консолі).

### PLY-3 · Критично · Зайві та чутливі permissions — ✅ Виправлено 2026-08-12

`android/app/src/main/AndroidManifest.xml`: `RECORD_AUDIO`, `SYSTEM_ALERT_WINDOW`, `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`, `requestLegacyExternalStorage="true"`.

Мікрофон приходив із `expo-image-picker` (запис відео), storage — з `react-native-fs` / `expo-media-library`, які **в коді не використовуються** (0 імпортів). Обґрунтувати мікрофон і overlay у D&D-компаньйоні нічим — довгий review, часто відмова.

**Перевірено 2026-08-12:** `RECORD_AUDIO`, `SYSTEM_ALERT_WINDOW` і `requestLegacyExternalStorage="true"` вже були прибрані з `AndroidManifest.xml`. `READ_EXTERNAL_STORAGE`/`WRITE_EXTERNAL_STORAGE` теж прибрано цим проходом — пакети, що їх вимагали (`react-native-fs`, `expo-media-library`), відсутні в `package.json` (див. PERF-3), і `app.json` не декларує `android.permissions`, тож правки лише в `AndroidManifest.xml` достатньо. Усі чотири пункти закриті.

### PLY-4 · Критично · Реліз підписується debug-keystore

`android/app/build.gradle`: `release { signingConfig signingConfigs.debug }`. Play відхиляє debug-підписані AAB. EAS зазвичай підставляє свої credentials, але **перевіряти треба на реальному артефакті**. Окремо: після налаштування Play App Signing з'явиться новий SHA-1, і його треба додати у Firebase + OAuth client, інакше Google Sign-In зламається саме в проді.

### PLY-5 · Високий · Донати й крипта на екрані підтримки

`src/screens/Support/Support.tsx:7-12` — PrivatBank, monobank jar, адреса USDT TRC20. Дві політики Play одночасно: Payments (обхід Play Billing) і Financial products (крипта). Мінімум — прибрати крипто-гаманець; по банківських посиланнях ухвалити свідоме рішення.

### PLY-6 · Високий · Версіонування: `versionName` живе в gradle, не в `app.json`

Уточнено в v2. У bare-проєкті (а він саме bare, бо `android/` закомічений і prebuild не запускається) `versionName` береться з `android/app/build.gradle`. Тобто підйом до 1.0.0 треба зробити **в обох місцях**:

- `app.json` → `"version": "1.0.0"`;
- `android/app/build.gradle` → `versionName "1.0.0"`.

Чому це не косметика: якщо `runtimeVersion` буде з політикою `appVersion`, runtime OTA рахується з `app.json`, а стор показує gradle-значення. Розбіжність = апдейти летять не в ту збірку. `versionCode` не чіпати руками — ним керує EAS (`appVersionSource: "remote"`); після першого білда зафіксувати фактичне значення.

### PLY-7 · Високий · Edge-to-edge тепер обов'язковий (targetSdk підтверджено = 36)

У v1 це був пункт «перевірити». Перевірено: `react-native/gradle/libs.versions.toml` → `targetSdk = "36"`, `compileSdk = "36"`, `minSdk = "24"`; `settings.gradle` викликає `expoAutolinking.useExpoVersionCatalog()`, `app/build.gradle` бере `rootProject.ext.targetSdkVersion`.

Добра новина: вимога Play «API 36 до 31.08.2026» виконана. Погана: при targetSdk 36 системний opt-out від edge-to-edge не діє, а в `android/gradle.properties` стоїть `expo.edgeToEdgeEnabled=false`. Отже на Android 15+ система малює edge-to-edge незалежно від флага, а `react-native-edge-to-edge` не підключений.

Часткова компенсація вже є: `react-native-safe-area-context` + `useSafeAreaInsets` у `AppNavigator`. Але треба пройтися по модалках, sticky-футерах (`CreateCharacter`), `ScrollView` без bottom padding і статус-барах на реальному Android 15/16.

Окремо перевірити відповідність вимозі **16 KB page size** (RN 0.81/Expo 54 її підтримують; Play попередить у консолі).

### PLY-8 · Середній · Trademark у store listing

У метаданих Play не використовувати «Dungeons & Dragons» і логотипи Wizards. «Mythgate 5e Companion» + атрибуція SRD 5.1 за CC-BY-4.0 (не OGL 1.0a — Wizards випустили SRD 5.1 під Creative Commons Attribution 4.0 як окрему, простішу ліцензію; текст обов'язкової атрибуції — `dnd.wizards.com/resources/systems-reference-document`, локальна копія `.agents/docs/SRD_CC_v5.1.pdf`) — безпечна рамка. Ліцензія прямо дозволяє формулювання «5E compatible». Юридичну оцінку роби окремо, це не висновок аудиту.

## 2. Безпека (SEC)

### SEC-1 · Високий · Будь-який авторизований читає всю колекцію `users`
```
match /users/{userId} { allow read: if isSignedIn(); … }
```
`read` = `get` + `list` → перелічення всієї бази користувачів. Треба `get` лише для себе й пов'язаних, `list` заборонити, пошук по email — через `emailIndex`.

### SEC-2 · Критично · Захоплення `emailIndex` (найсерйозніше)
```
match /emailIndex/{emailLower} {
  allow create, update: if isSignedIn() && request.resource.data.uid == uid();
}
```
Немає перевірки, що **існуючий** документ належить тому ж користувачу → будь-хто перезапише `emailIndex/victim@example.com` своїм `uid`. Далі шаринг по email (`src/services/users.ts:24`) віддасть аркуш атакуючому. **З кількома редакторами це прямий шлях до чужого персонажа з правом запису.**

Фікс: `create: … && resource == null`, `update: … && resource.data.uid == uid()`, `list` заборонити.

### SEC-3 · Високий · Немає валідації форми документів при create/update
Ні для `characterSheets`, ні для `dmCampaigns`/`dmCampaignNotes` не перевіряються `keys()`, типи, довжини, розміри масивів. Будь-який запрошений редактор може писати документ довільної форми (див. також COL-8).

### SEC-4 · Середній · `connections`: `update: if isParticipant()` без immutability
Учасник може переписати `fromUid`/`toUid`. Зафіксувати незмінні поля так само, як зроблено для `characterSheets`.

### SEC-5 · Високий · `users` має `allow delete: if false`
Прямо конфліктує з PLY-1. Потрібен дозвіл власнику або каскад через Cloud Function.

### SEC-6 · Високий · Мертвий код звертається до колекцій без правил — ✅ Виправлено 2026-08-12
`src/shared/services/firestore/{firestore.ts,pdocs.ts,sharing.ts,loger.ts}` ніде не імпортуються (крім `pdocs → sharing`), але працюють із `docs`, `docShares`, `sharedDocs`, `demoItems` (яких немає в `firestore.rules`) і роблять `addDoc(collection(fs,'users'), …)`, тобто створюють сміттєві документи в `users` з випадковими id. **Видалити всі чотири файли** (~700 рядків).

**Перевірено 2026-08-12:** директорія `src/shared/services/firestore/` не існує — усі чотири файли видалено.
