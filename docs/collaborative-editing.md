# Спільне редагування аркуша персонажа: аудит і цільова модель

Дата: **2026-07-26** · Куди покласти: `docs/collaborative-editing.md`
Контекст: один аркуш персонажа редагують кілька людей (типово гравець + DM, іноді кілька гравців). Це не «шаринг для перегляду», а справжнє паралельне редагування під час живої сесії.

---

## 1. Що вже реалізовано (і зроблено непогано)

Перед критикою — фактичний стан, бо модель складніша, ніж «залив документ у хмару»:

| Механізм                  | Де                                                                                                | Що робить                                                                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Роли доступу              | `firestore.rules`, `characterCloudRepository.ts`                                                  | `ownerUid`, `owners[]`, `editors[]`; editor може писати вміст, але не змінювати склад доступу                                                                        |
| Live-підписка на аркуш    | `useCharacterActions.tsx:610` (`subscribeCharacterSheet`)                                         | Чужі зміни приходять у відкритий екран у реальному часі                                                                                                              |
| Журнал змін               | `changeHistory[]`, `buildHistoryEntries`, `mergeBoundedHistory` (обмеження 50)                    | Хто (`uid`), яка роль (`actorRole`), який таб, які шляхи, коли (`atMs`)                                                                                              |
| Виявлення віддалених змін | `useCharacterActions.tsx:628-632`                                                                 | Із `changeHistory` беруться записи інших `uid` після `lastSyncAt` → `remotePathsSinceLastSync`                                                                       |
| Секційний merge           | `mergeCharacterBySections` у `characterSyncCoordinator.ts`                                        | Якщо локально немає pending-змін у секції — секція повністю береться з хмари                                                                                         |

Тобто фундамент є: підписки, журнал, секційний merge, явні стани, ручне розв'язання. Проблеми — у конкретних місцях, і вони виправляються точково.

## 2. Знахідки (COL-\*)

### COL-1 · Критично · Read-modify-write без транзакції → тиха втрата чужих змін

`characterCloudRepository.ts:409-447` (`upsertCharacterSheetFromLocal`):

```
const snap = await ref.get();                       // 1. читаємо
const payload = buildCloudDocFromLocal(dto, me, …); // 2. будуємо ВЕСЬ документ з локального стану
await ref.set(payload, { merge: true });            // 3. пишемо ВЕСЬ документ
```

`merge: true` тут не рятує: payload містить **усі** поля персонажа, тож він перекриває кожне з них. Сценарій втрати:

1. Гравець і DM обидва мають аркуш відкритим.
2. DM тисне «−7 HP» → його клієнт читає документ, пише повний payload.
3. Гравець за секунду до цього поставив condition → його клієнт вже прочитав документ **до** правки DM і пише свій повний payload.
4. Останній запис перемагає повністю. Зміна DM зникає без жодного індикатора — це не конфлікт-модалка, це просто тихо загублені дані.

Ризик особливо високий саме в бою, бо там частота правок максимальна.

**Фікс:** `runTransaction` для upload (перечитати документ у транзакції та змерджити) або перейти на точкові `update()` по конкретних змінених шляхах, використовуючи вже наявний `pendingPaths` як список того, що реально треба записати. Другий варіант кращий: він і швидший, і природно вирішує COL-4.

---

### COL-2 · Критично · `changeHistory` перезаписується → ламається виявлення віддалених змін

`characterCloudRepository.ts:429`:

```
payload.changeHistory = mergeBoundedHistory(existingMeta?.changeHistory, additions, 50);
```

Історія збирається з **застарілого** читання і записується як цілий масив. Наслідки:

- запис редактора A стирає щойно додані записи редактора B;
- а на `changeHistory` тримається `remotePathsSinceLastSync`. Немає записів → `reconcileRemoteSnapshot` вважає, що в хмарі нічого не змінилось → при наявних локальних `pendingPaths` повертає `noop` → чужа зміна **не застосовується локально**, а наступний upload її перезаписує.

Тобто COL-2 робить COL-1 частішим і невидимішим.

Додатково: ліміт 50 записів. У сесії з двома активними редакторами 50 записів набігає швидко; після переповнення старіші зміни зникають із журналу, і клієнт, який довго був офлайн, «не побачить» їх зовсім.

**Фікс:**

- додавання історії — тільно `arrayUnion(...additions)` (уже експортований у `src/services/firebase.ts:10`), ніколи не цілим масивом;
- або перенести журнал у підколекцію `characterSheets/{id}/changes` з `serverTimestamp()` — це знімає і ліміт 50, і розмір документа, і дає нормальні запити «що змінилось після X»;
- обрізання історії робити окремою операцією обслуговування, а не в шляху запису.

---

### COL-3 · Критично · `owners`/`editors` пишуться зі stale-read

`characterCloudRepository.ts:433-440`:

```
if (existingMeta) {
  payload.owners  = existingMeta.owners  || [me];
  payload.editors = existingMeta.editors || [];
}
```

Два різні збої, залежно від того, хто пише:

- **Пише owner.** Він щойно (в іншому клієнті або з екрана шарингу) додав редактора; його старий знімок ще не має цього редактора → запис **відкатує доступ**. Людина втрачає права без жодного повідомлення.
- **Пише editor.** Правило вимагає `request.resource.data.editors == resource.data.editors`. Якщо склад редакторів змінився між читанням і записом — умова не виконується → `PERMISSION_DENIED`. А в шляху upload помилки місцями глушаться (`bulkUpsertFromLocal` має порожній `catch`), тож користувач бачить лише те, що синк «не доїжджає».

**Фікс:** прибрати `owners`/`editors`/`ownerUid` із payload звичайного upload узагалі. Склад доступу змінюють **тільки** окремі транзакційні операції (`addEditorByEmail`, `removeEditor`, `transferOwnership`) — вони вже частково існують на рядках 490-510 і використовують `tx.update`. Правило Firestore тоді стає простішим і надійнішим.

---

### COL-4 · Високий · Секційна гранулярність надто груба для бою

`conflictPolicy.ts` + `mergeCharacterBySections`: секція `combat` включає `hp`, `ac`, `initiative`, `speed`, `hitDice`, `deathSaves`, `weapons`, `conditions`, `combatTemplates`, `sessionMode`.

`collectConflictPaths` еквалює будь-який перетин **на рівні секції**:

```
const section = pathToSyncSection(path);
if (section !== 'unknown' && cloudSections.has(section)) { out.push(path); }
```

Отже DM змінює HP, гравець одночасно ставить `condition` → різні поля, але одна секція → **конфлікт-модалка**. Або, якщо pending немає, merge затягне всю секцію з хмари й локальна зміна зникне.

У живій сесії це найчастіший сценарій із усіх можливих. Продуктовий наслідок: або людей засипає конфліктами, або вони тихо втрачають правки — обидва варіанти вбивають довіру до спільного аркуша.

**Фікс (поетапно):**

1. Розбити `combat` на під-секції: `combat.vitals` (hp, tempHp, deathSaves), `combat.defense` (ac, speed, initiative, hitDice), `combat.conditions`, `combat.weapons`. Аналогічно `homebrew` (`resources`/`trackers`/`fields`/`sections`) — там теж критичні шляхи.
2. Для числових «лічильників» (HP, spell slots, resources) перейти від «останній переміг» до **семантичного merge**: писати дельту (`FieldValue.increment`) або зберігати `{value, updatedAt, updatedBy}` на полі й брати свіжіше за серверним часом. HP — це не текст, це рахівниця; два одночасні `−7` і `+2` мають дати `−5`, а не «хтось один».
3. `conditions` — це множина: `arrayUnion`/`arrayRemove` замість заміни масиву.

Пункт 1 — обов'язковий до релізу. Пункти 2–3 — за наявності часу, інакше одразу після 1.0 (винести в беклог, а не «колись»).

### COL-5 · Виправлено · Порівняння часу на клієнтських годинниках

Було: `changeHistory[].atMs = Date.now()` (час клієнта, що пише) порівнювався напряму із
`syncState.lastSyncAt` (час клієнта, що читає) через `entry.atMs > (syncState?.lastSyncAt || 0)`.
Розбіжність годинників між девайсами (звична річ: різні часові налаштування, дрейф, ручне
переведення) давала два симетричні збої: годинник того, хто пише, «відстає» → його зміни
виглядають як старі й ігноруються; «біжить уперед» → зміни застосовуються повторно нескінченно.

**Реалізований фікс** (`characterSyncCoordinator.ts`, `characterCloudRepository.ts`,
`useCharacterActions.tsx`): `serverTimestamp()` не можна класти всередину елементів масиву
`arrayUnion`, тому буквальний "серверний час на кожен запис журналу" вимагав би підколекції
(окрема задача, див. нижче). Мінімальний варіант без підколекції:

1. Документ `characterSheets` отримав нове поле `lastChangeAt = now()` (serverTimestamp),
   яке бампається одночасно з кожним додаванням `changeHistory`. `syncState.lastSyncAt` тепер
   зберігає саме цей серверний час останнього оброненого знімка, а не локальний `Date.now()`.
2. Точний відбір "які саме paths нові" зроблено **не порівнянням часу**, а diff-ом за
   стабільним `entry.id` (`computeRemoteHistorySync` у `characterSyncCoordinator.ts`) —
   `CharacterSyncState.seenHistoryEntryIds` тримає список уже врахованих id. Це повністю
   незалежне від будь-якого годинника, зокрема й від ручної зміни годинника на ОДНОМУ
   пристрої посеред сесії — кейс, який порівняння по `atMs` (навіть "по автору") не покриває.

**Заплановано окремою задачею:** міграція `changeHistory` в підколекцію
`characterSheets/{id}/changes` з реальним `serverTimestamp()` на кожен запис — дозволить
валідацію в `firestore.rules` і зніме необмежене зростання масиву (перетинається з COL-9).
Не зроблено зараз, бо чіпає >1 файл (репозиторій, координатор, хук підписки, rules, DM-екран
історії).

### COL-6 · Середній · Немає presence — не видно, хто зараз в аркуші

Немає жодної індикації «DM щойно відкрив цей аркуш» / «гравець редагує Combat». Через це:

- конфлікти виглядають випадковими, бо користувач не знає, що хтось ще в документі;
- люди не мають шансу скоординуватись голосом («не тягни HP, я вже пишу»), хоча за столом це найдешевший спосіб.

**Фікс (дешевий варіант, достатній для 1.0):** у `changeHistory` уже є `uid`, `actorRole`, `tab` і час. Показувати в шапці аркуша тонкий рядок «DM оновив Combat 12 с тому» на основі останнього запису журналу. Це не справжній presence, але дає 80% ефекту без нової інфраструктури.

**Повний presence** (підколекція `presence/{uid}` з heartbeat) — після 1.0, це додаткові записи й квота.

### COL-7 · Середній · Помилки шляху синку глушаться

- `bulkUpsertFromLocal` (`characterCloudRepository.ts:449-455`) — порожній `catch` на кожному персонажі.
- `characterLocalRepository.saveCharacters:48` — `catch (_error) { /* intentionally ignored */ }`.
- У `useCharacterActions.tsx` низка `.catch(() => {})` на маркерах синку.

З одним користувачем це «неприємно». З кількома редакторами це означає, що `PERMISSION_DENIED` із COL-3 і будь-яка інша відмова запису **невидимі**: людина думає, що зміна збережена, а її немає ні локально, ні в хмарі.

**Фікс:** відрізняти «очікувані» помилки (офлайн → у чергу) від «неочікуваних» (permission-denied, invalid-argument, quota) і для других показувати toast + подія телеметрії `permission_denied_on_upload` / `sync_failed`.

---

### COL-8 · Середній · Правила не валідують те, що пишуть редактори

`firestore.rules` для `characterSheets` перевіряє незмінність `ownerUid`/`owners`/`editors`, але **не перевіряє нічого іншого**: ні набір полів, ні типи, ні розміри. Редактор (тобто будь-хто, кого запросили) може записати документ довільної форми, роздути його або зламати схему для решти учасників.

**Фікс:** мінімальна валідація на create/update — обов'язкові ключі, типи критичних полів, обмеження довжини текстових полів і розміру масивів (`notes`, `inventory`, `homebrewEntries`, `changeHistory`).

---

### COL-9 · Середній · Ризик 1 MiB на документ

Аркуш містить inventory, notes blocks, custom sections, homebrew entries, spell lists **плюс** до 50 записів `changeHistory` — усе в одному документі. Ліміт Firestore — 1 MiB. Із активним homebrew і довгими нотатками це реально досяжно, а при перевищенні запис просто падає — і, через COL-7, падає тихо.

**Фікс:** (а) зміряти реальний розмір найбільших документів у проді/тесті; (б) винести `changeHistory` у підколекцію (це і так треба за COL-2); (в) додати захисне логування, коли документ перевищує ~700 КБ.

---

### COL-10 · Високий · Видалення акаунта при спільних аркушах

Прив'язано до Play-блокера PLY-1 (обов'язкове видалення акаунта). З кількома редакторами наївне «видалити всі мої `characterSheets`» знищить дані інших людей.

**Правильна логіка каскаду:**

| Ситуація                          | Дія                                                                                       |
| --------------------------------- | ----------------------------------------------------------------------------------------- |
| Я єдиний owner, редакторів немає  | видалити документ                                                                         |
| Я єдиний owner, є редактори       | передати ownership першому редактору (або запитати користувача), себе прибрати з `owners` |
| Я один із кількох owners          | прибрати себе з `owners`                                                                  |
| Я тільно editor                   | прибрати себе з `editors`                                                                 |
| `connections`, де я учасник       | позначити неактивними або видалити                                                        |
| `emailIndex/{my-email}`           | видалити                                                                                  |
| `users/{myUid}`                   | видалити (потрібне правило, зараз `delete: if false`)                                     |
| `dmCampaigns` / `dmCampaignNotes` | та сама логіка owner/editor                                                               |

Це неможливо зробити консистентно з клієнта під правилами: після видалення `users/{uid}` і виходу з акаунта клієнт уже не має прав добивати решту. **Рішення:** Cloud Function на `onDelete` користувача Auth (або callable-функція «видалити мій акаунт»), яка виконує каскад із адмін-правами. Це єдине місце в плані, де знадобиться серверний код — врахуй у часі.

## 3. Цільова модель (мінімум для 1.0)

Порядок написання коду:

1. **Розділити операції на дві категорії:**
   - _content write_ — вміст персонажа. Ніколи не торкається `ownerUid`/`owners`/`editors`. Пише **тільно змінені шляхи** (з `pendingPaths`) через `update()`, або цілий документ у `runTransaction`.
   - _access write_ — склад доступу. Тільно транзакції `addEditor` / `removeEditor` / `transferOwnership`. Ніколи не пишуть вміст.
2. **Журнал змін** — `arrayUnion` (швидкий фікс) або підколекція `changes` із `serverTimestamp()` (правильний фікс).
3. **Час — серверний** для журналу й `lastSyncAt`.
4. **Секції дрібніші**: `combat.vitals` / `combat.defense` / `combat.conditions` / `combat.weapons`; `homebrew.*` за під-типами.
5. **Помилки видимі**: permission-denied і quota → toast + телеметрія; офлайн → тиха черга (як зараз).
6. **«Хто щойно правив»** у шапці аркуша з наявного журналу.
7. **Каскадне видалення акаунта** через Cloud Function.
8. **Правила**: закрити SEC-1…SEC-4, додати валідацію форми документа (COL-8), додати `delete` для `users` власником.

Що **не** робимо до 1.0: CRDT/OT, офлайн-мердж довільної глибини. ~~Справжній
presence, поле-рівневі дельти для всього документа~~ — **перенесено в 1.0-scope
2026-09-01** (`CLAUDE.md` Виняток 3), див. §3.1 нижче. Поточна модель із дрібнішими
секціями та транзакціями вже закриває більшість сценаріїв застілля; §3.1 закриває
залишок (лічильники, presence, розмір документа) під час нового 14-денного вікна.

### 3.1 Виняток від 2026-09-01: COL-4 повністю + COL-6 + COL-9

Свідомо перенесено з «після 1.0» в 1.0-scope рішенням власника продукту
2026-09-01 — див. `CLAUDE.md` Виняток 3 і `docs/release-plan-google-play.md` R5
(R5-0a/R5-0b). Причина: 14-денне вікно закритого тесту (старт 2026-08-31) все
одно безкоштовне з погляду інженерного часу, а це технічне зміцнення точки, яка
вже найчастіше провокує конфлікти в живій сесії.

**COL-4 повністю (семантичний merge лічильників):**

- Числові «лічильники» (`combat.vitals.hp`/`tempHp`, `magic.spellSlots.*.used`,
  `homebrew.resources.*.current`) переходять із «останній переміг» на дельти:
  клієнт рахує *зміну* (`+2`/`-7`), а не абсолютне значення, і пише її через
  `FieldValue.increment(delta)` замість цілого числа.
- `combat.conditions` (і аналогічні множини) — `arrayUnion`/`arrayRemove`
  конкретного елемента замість заміни всього масиву.
- Наслідок для конфліктів: `collectConflictPaths` для цих конкретних полів
  більше не повинен показувати conflict-модалку при одночасному записі двома
  редакторами — Firestore сам застосує обидві дельти атомарно на сервері.
  Точковий livemerge полів, що НЕ є лічильниками (текстові нотатки, вибір
  зі списку) — без змін, лишається «останній переміг» + секційний конфлікт.
- Ризик: `increment()` не має верхньої межі (наприклад, HP не може перевищити
  `maxHp`) — clamp/валідацію максимуму робити на читанні (UI), не покладатися,
  що сервер обмежить значення.

**COL-6 (presence) + COL-9 (підколекція журналу) — одна міграція, бо обидва
чіпають ту саму площину «дані поза основним документом»:**

- Нова підколекція `characterSheets/{id}/changes/{entryId}` — кожен запис
  журналу окремим документом із `serverTimestamp()`, замість масиву
  `changeHistory[]` у самому документі персонажа. Знімає ліміт 50 записів і
  ризик 1 MiB (COL-9), дає нормальний `serverTimestamp()` на кожен запис
  (продовження COL-5, яке раніше довелось обійти саме через відсутність
  підколекції).
  - **UI, що читає `changeHistory[]`, доведеться переписати на підписку до
    підколекції**: `useCharacterActions.tsx` (`subscribeCharacterSheet` і
    похідна логіка `remotePathsSinceLastSync`), `DMSharedUpdates.tsx`,
    `Character.tsx` («N хв тому»). Це найбільший обсяг зміни в цій парі задач.
  - `firestore.rules` — нові правила для підколекції `changes` (create-only
    для editor/owner, без update/delete з клієнта; ті самі перевірки доступу,
    що й для батьківського документа).
  - Міграція існуючих `changeHistory[]` у підколекцію — one-time скрипт або
    лінива міграція при першому записі (простіше й безпечніше: не займатись
    ретроактивною міграцією історичних записів, почати підколекцію «з нуля»
    з моменту релізу; старий масив можна лишити як deprecated поле або
    прибрати окремим PR після підтвердження, що ніхто на нього не покладається).
- Presence (`characterSheets/{id}/presence/{uid}`) — окремий документ на
  користувача з `lastActiveAt: serverTimestamp()`, оновлюється heartbeat'ом
  (наприклад, раз на 20-30 с, поки екран персонажа відкритий, і видаляється/
  позначається неактивним при `onDisappear`/unmount). У шапці аркуша — рядок
  «DM тут» / «DM був 2 хв тому» на основі найсвіжішого `lastActiveAt` серед
  інших `uid`. Дешевша версія (наявний журнал) — вже описана вище як
  fallback, якщо повний heartbeat не встигне до кінця вікна.
  - Квота: TTL/очищення presence-документів (наприклад, ігнорувати записи
    старіші за N хвилин на клієнті, замість Cloud Function на видалення) —
    щоб не накопичувати сирітські документи від людей, що закрили застосунок
    без чистого unmount.

**DoD для цього виключення** (додатково до §9 CLAUDE.md): тести на двох
клієнтах — (1) DM і гравець одночасно тричі поспіль б'ють по HP (`-3`, `+1`,
`-2`) → фінальне значення на обох клієнтах правильне без конфлікт-модалки;
(2) обидва одночасно ставлять різні conditions → обидва застосувались;
(3) підколекція `changes` росте, `changeHistory[]` у документі більше не
використовується для нового запису; (4) presence видно на другому клієнті
протягом кількох секунд після відкриття аркуша й зникає після закриття.

## 4. Тест-план (без нього не вважати зробленим)

Спільне редагування **неможливо перевірити на одному клієнті**. Потрібні два: емулятор + фізичний девайс, два різні Google-акаунти (owner і editor).

**Юніт/інтеграційні (vitest)**

- [ ] `collectConflictPaths` після дроблення секцій: HP vs condition → **не конфлікт**; HP vs HP → конфлікт.
- [ ] `mergeCharacterBySections` на нових під-секціях.
- [ ] `reconcileRemoteSnapshot`: `replace` / `merge` / `conflict` / `noop` на серверних таймстемпах.
- [ ] Каскад видалення акаунта: усі чотири випадки owner/editor із таблиці COL-10.
- [ ] Content write не містить `owners`/`editors`/`ownerUid` у payload.

**Правила (firebase emulators:exec)**

- [ ] editor не може змінити `editors`/`owners`/`ownerUid`.
- [ ] сторонній користувач не читає й не пише аркуш.
- [ ] не можна перезаписати чужий `emailIndex` (SEC-2).
- [ ] `list` по `users` заборонений (SEC-1).
- [ ] owner може видалити себе з `users` (для PLY-1).
- [ ] документ із зайвими/невалідними полями відхиляється (COL-8).

**Два клієнти, вручну**

- [ ] Одночасно: DM тисне −7 HP, гравець ставить condition → **обидві зміни збереглися**, конфлікт-модалки немає.
- [ ] Одночасно обидва правлять HP → конфлікт показаний, розв'язання працює, після нього стан однаковий на обох.
- [ ] Owner додає редактора, поки редактор активно щось пише → доступ не відкатився, `PERMISSION_DENIED` не з'явився.
- [ ] Editor офлайн править 3 секції → онлайн → усе доїхало, чужі зміни не втрачені.
- [ ] Годинник одного девайса зсунутий на ±10 хвилин → синк усе одно коректний (перевірка COL-5).
- [ ] Editor виходить, owner видаляє акаунт → аркуш не зник у редактора, ownership передано.
- [ ] У шапці видно «DM оновив Combat N с тому».
- [ ] 30 хвилин активної сесії двох клієнтів → порахувати читання/записи Firestore у консолі, порівняти з безкоштовною квотою.
