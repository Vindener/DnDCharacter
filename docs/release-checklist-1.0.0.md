# Реліз-чекліст 1.0.0

Джерела: `docs/release-plan-google-play.md` §4 (регресійний чекліст) + `docs/collaborative-editing.md` §4 (тест-план). Обидва документи описували частково однакові два-клієнтські сценарії різними словами — тут вони змерджені в один пункт без дублювання. Нічого понад те, що вже було в цих двох документах, сюди не додано.

Групування — за тим, **чим** перевіряється, а не за тим, до якого спринту належить.

---

## (а) Автоматично командами

Один прогін:

```bash
npm run release:check
```

Послідовно запускає всі шість кроків нижче, продовжує навіть якщо один крок впав (щоб побачити повну картину за один раз), друкує зведення ✅/❌ і завершується ненульовим кодом, якщо хоч щось не пройшло.

- [ ] `typecheck` — `tsc --noEmit`
- [ ] `lint` — ESLint (`src`, `App.tsx`, `index.js`)
- [ ] `lint:theme` — заборонені кольорові літерали поза `theme.ts`
- [ ] `test:unit` — vitest, увесь юніт/інтеграційний набір
- [ ] `validate:srd` — Zod-валідація 11 SRD-колекцій (build-time, P3.2)
- [ ] `test:rules` — Firestore rules у `firebase emulators:exec` (P2.3)

**Що саме перевіряють `test:unit` і `test:rules` зсередини** (довідково — не окремі чекбокси, вони вже входять у прогони вище):

`test:unit`:
- `collectConflictPaths` після дроблення секцій: HP vs condition → не конфлікт; HP vs HP → конфлікт
- `mergeCharacterBySections` на нових під-секціях
- `reconcileRemoteSnapshot`: `replace`/`merge`/`conflict`/`noop` на серверних таймстемпах
- Каскад видалення акаунта: усі чотири випадки owner/editor з таблиці COL-10
- Payload запису не містить `owners`/`editors`/`ownerUid`

`test:rules` (`firebase emulators:exec`):
- editor не може змінити `editors`/`owners`/`ownerUid`
- сторонній користувач не читає й не пише чужий аркуш
- не можна перезаписати чужий `emailIndex` (SEC-2)
- `list` по `users` заборонений (SEC-1)
- owner може видалити себе з `users` (PLY-1)
- документ із зайвими/невалідними полями відхиляється (COL-8)

## (б) Вручну — один пристрій

Прогнати **на release-білді** (не dev-client), на реальному Android-девайсі, **на чистій установці**, якщо не вказано інше.

**Офлайн / базовий UX**
- [ ] Перший запуск на чистій установці: сплеш → Home без білого екрана й без крашу — ловить PERF-5, REL-1
- [ ] Створення персонажа повністю офлайн і без логіну (візард, скрол, клавіатура не перекриває поля) — ловить порушення локально-першого режиму (`CLAUDE.md §3.8`)
- [ ] Перезапуск застосунку → персонаж на місці — ловить регресії AsyncStorage/міграцій
- [ ] Character Sheet: HP/AC/initiative, Play vs Edit, Quick Action Bar — загальна UX-регресія
- [ ] Dice Roller: d20 + модифікатор + advantage/disadvantage, історія — загальна UX-регресія
- [ ] Spellbook: пошук, фільтри, prepared/known/favorites — загальна UX-регресія
- [ ] Bestiary: пошук, фільтри, деталі, pin — загальна UX-регресія, дотично PERF-6 (FlatList-тюнінг)
- [ ] DM: кампанії, нотатки, encounter prep, initiative — загальна UX-регресія
- [ ] Імпорт бестіарію з файлу, експорт/шаринг персонажа — регресія файлових операцій
- [ ] Перемикання uk/en і світла/темна тема на головних екранах — регресія i18n/теми

**Онлайн, але один пристрій**
- [ ] Google Sign-In у білді, встановленому **з Play** (не лише локальний білд) — ловить неправильний SHA-1/OAuth client для Play App Signing (`CLAUDE.md §8.4`)
- [ ] Авіарежим → відновлення мережі → pending-sync доїжджає — ловить регресії офлайн-черги, дотично REL-2

**Реліз-специфіка (потрібен фінальний AAB/білд)**
- [ ] Smoke-тест саме на **minify+shrink** білді — найризикованіша зміна, R8 ламає рефлексію (PERF-2)
- [ ] `aapt dump permissions` на фінальному AAB — лише очікувані дозволи (PLY-3)
- [ ] Edge-to-edge перевірено на Android 15/16 (PLY-7)
- [ ] Немає `console.*` у logcat release-білда (SEC-9)
- [ ] `eas update --branch production` опубліковано → встановлений білд підхоплює апдейт після повного перезапуску — перевіряє сам механізм EAS Update (R4-2)

## (в) Вручну — два пристрої, два акаунти

Без цього реліз не вважається готовим. Емулятор + фізичний девайс (або два фізичні), два різні Google-акаунти: **owner** і **editor** (одна роль — GM, інша — гравець, або навпаки).

- [ ] DM тисне −7 HP, гравець одночасно ставить condition → **обидві зміни збереглися**, конфлікт-модалки немає — ловить **COL-1** (read-modify-write без транзакції — тиха втрата чужих змін)
- [ ] Обидва одночасно правлять HP → конфлікт показаний; після розв'язання стан однаковий на обох клієнтах — ловить **COL-4** (секційна гранулярність merge/конфліктів)
- [ ] Owner додає редактора, поки редактор активно щось пише → доступ не відкотився, `PERMISSION_DENIED` не з'явився — ловить **COL-3** (`owners`/`editors` пишуться зі stale-read)
- [ ] Editor офлайн правив 3 секції → онлайн → усе доїхало, чужі зміни не втрачені — ловить **COL-2** (`changeHistory` перезаписується цілим масивом)
- [ ] Годинник одного девайса зсунутий на ±10 хв → синк усе одно коректний — ловить **COL-5** (порівняння часу на клієнтських годинниках)
- [ ] Owner видаляє акаунт (за потреби — editor попередньо вийшов) → аркуш **не зникає** в editor'а, ownership передано — ловить **COL-10** + **PLY-1** (видалення акаунта при спільних аркушах)
- [ ] У шапці листа видно «DM оновив Combat N с тому» — ловить регресію виявлення віддалених змін (та сама причина, що й **COL-2**: без коректного `changeHistory` цей маркер не з'явиться)
- [ ] 30 хв активної сесії двох клієнтів → порахувати читання/записи Firestore в консолі, порівняти з безкоштовною квотою — ловить **PERF-8** (кількість підписок Firestore)
- [ ] Збереження в хмару → синк на другому девайсі — базова перевірка хмарної синхронізації (можна тим самим акаунтом на 2 пристроях)
- [ ] Шаринг по email → приймання **іншим акаунтом** — базова перевірка запрошення редактора

## Коротко: що перевіряти після кожного OTA-апдейту

OTA (`eas update`) доставляє **лише JS і статичні асети** — жодних нативних змін, permissions чи іконок. Тому повний прогін вище не потрібен щоразу; цей блок коротший.

**Завжди, автоматично:**
- [ ] `npm run release:check` — швидкий (секунди), сенсу пропускати немає

**Завжди, вручну, один пристрій:**
- [ ] `eas update --branch production` опубліковано → встановлений білд підхоплює апдейт після повного перезапуску (не hot-reload) — той самий пункт, що й у групі (б), це і є перевірка самого механізму доставки хотфіксу

**Вибірково, вручну — лише те, що реально зачепив цей патч:**
- [ ] Пройдіться по відповідних пунктах з «Офлайн / базовий UX» (група б) — тільки по екранах/функціях, які змінилися в цьому патчі, не по всьому списку
- [ ] Якщо патч чіпав логіку синку/конфліктів — відповідні пункти з групи (в) усе ще актуальні (OTA не звільняє від COL-* перевірок, якщо змінено саме цю логіку)

**НЕ потрібно для звичайного OTA-патчу** (бо не може змінитися без нового AAB):
- Smoke-тест minify+shrink, `aapt dump permissions`, edge-to-edge, Google Sign-In у білді з Play — усе це про нативну частину, яку OTA не чіпає.
