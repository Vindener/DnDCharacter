9. **PLY-1 — `deleteMyAccount` повертає `NOT_FOUND` на реальному пристрої
   (виявлено 2026-08-12, скрін від власника продукту).** Клієнтський код і
   Cloud Function (`functions/src/deleteMyAccount.ts`, регіон `us-central1`,
   проєкт `mythgatednd` — збігається з `google-services.json`) виглядають
   коректно; `functions/lib/*.js` вже збілджені локально. `NOT_FOUND` — це
   код помилки Firebase Functions callable-клієнта саме для «функція не
   знайдена на бекенді», той самий симптом, що вже задокументований у коді
   для `createCampaignInvite` (`DMCampaignDetail.tsx:176-181`). Найвірогідніша
   причина — **`deleteMyAccount`/`createCampaignInvite`/`redeemCampaignInvite`
   ще не задеплойені** на проєкт `mythgatednd`, або не виконано one-time
   Console-передумови з `functions/README.md` (Blaze-план замість Spark,
   увімкнені Cloud Functions/Cloud Build/Artifact Registry/Eventarc API) —
   без Blaze-плану 2nd-gen функції взагалі не деплояться. Це критично для
   Google Play: видалення акаунта — обов'язкова вимога (R1), і зараз вона
   не працює в проді. **Дію не можу виконати сам** — деплой потребує
   `firebase login` під акаунтом-власником проєкту й (можливо) підняття
   білінгу в Firebase Console, це поза можливостями цього середовища.
   Точкова правка зроблена: `DeleteAccountModal.tsx` більше не показує
   користувачу сирий код помилки (`NOT_FOUND`) — тепер завжди generic текст,
   за винятком `reauth-failed`.

   **Підтверджено спробою деплою 2026-08-12:** `firebase deploy` дійшов до
   кроку ввімкнення `artifactregistry.googleapis.com` і впав з `Error: Your
project mythgatednd must be on the Blaze (pay-as-you-go) plan` — причина
   підтверджена, це не гіпотеза.

   **Рішення власника продукту (2026-08-12):** перейти на Blaze +
   бюджетний алерт, а не переписувати каскад на клієнт без Cloud Functions.
   Обґрунтування: `onCall`-функції викликаються вручну (видалення акаунта,
   інвайт у кампанію) з масштабом закритого тесту ~12 людей — це на порядки
   нижче безкоштовної квоти 2nd-gen Cloud Functions (2 млн викликів/міс),
   очікувана вартість $0/міс. Альтернатива (клієнтський каскад через зміну
   `firestore.rules` + відмова від атомарної admin-транзакції) створює
   реальний ризик для security-межі проєкту за 3 тижні до релізу — обрано
   не робити.

firestore.rules to cloud.firestore`), API (`cloudbuild`, `artifactregistry`,

   **Новий блокер, знайдений на цьому кроці (той-таки день):** усі три
   функції впали на Cloud Build з `lib/index.js does not exist`. Причина —
   баг у `firebase.json`: `functions[0].ignore` містив `"lib"`. Локальний
   `predeploy`-скрипт (`npm run build`) справді компілює `functions/lib/`,
   але потім пакування джерела для завантаження в Cloud Build застосовує
   той-таки `ignore`-список і викидає щойно зібраний `lib/` з архіву — на
   боці Cloud Build код приїжджає без entry point (`main: "lib/index.js"`
   у `functions/package.json`). **Виправлено**: `"lib"` прибрано з
   `firebase.json` (рядок 9), лишились лише `node_modules`/`.git`/тести.

   Побічні варнінги з того ж запуску деплою (не блокери, не для зараз):
   Node.js 20 runtime deprecation (decommission 2026-10-30 — оновити
   `functions/package.json` `engines.node` заздалегідь, але не в цьому
   релізному вікні) і застаріла версія `firebase-functions` — обидва
   ігнорувати до 1.0, потім окрема задача.

   **Ще один блокер після успішного деплою (той-таки день):** усі три
   функції відповідали `UNAUTHENTICATED` на легітимні виклики з застосунку.
   Причина — Cloud Run-сервіси (2nd gen) деплоїлись з `Require
authentication` замість `Allow public access` на вкладці Security, тож
   запит відхилявся на рівні IAM ще до того, як код функції встиг

   Run Console (Services → `deletemyaccount`/`createcampaigninvite`/
   `redeemcampaigninvite` → Security → Allow public access) для всіх трьох
   сервісів. Це безпечно: усі три функції самі перевіряють
   `request.auth?.uid` у коді (`deleteMyAccount.ts:143`,
   `createCampaignInvite.ts:38`, `redeemCampaignInvite.ts:22`) — "публічний"
   тут лише транспортний рівень Cloud Run, авторизація лишається в коді.

   - `AndroidManifest.xml:37-42` декларує App Link `autoVerify="true"` лише
     для хосту `mythgatednd.pp.ua` (без `www.`), `pathPrefix="/join"`. Android
     верифікує App Link лише якщо на цьому ж хості за адресою
     `https://mythgatednd.pp.ua/.well-known/assetlinks.json` лежить файл із
     правильним `package_name` (`com.vind.MythgateDND`) і SHA-256 сертифіката
     підписання (той самий, що й для Google Sign-In, `docs/release-plan-google-play.md`
     §R1-2). Якщо цього файлу немає на сервері — верифікація мовчки не
     проходить, і посилання відкривається в браузері, а не в застосунку.
   - `AppNavigator.tsx` (`linking.prefixes`) очікує **обидва** варіанти —
     `https://mythgatednd.pp.ua` і `https://www.mythgatednd.pp.ua` — а
     нативний intent-filter задекларований лише на один хост без `www.`.
     Навіть після додавання `assetlinks.json` посилання на `www.`-варіант не
     верифікується Android App Links (точний збіг хосту, не піддомену) — це
     окрема нестиковка, яку варто виправити тим самим проходом.
   - Крім самої верифікації, на `https://mythgatednd.pp.ua/join/:code`
     потрібна **фолбек-сторінка** (як уже є для Privacy Policy й видалення
     акаунта на тому самому домені) — для користувачів без застосунку
     встановленого або якщо верифікація не спрацювала на конкретному
     пристрої/ОС.

   **Дію не можу виконати сам** — потрібен доступ до хостингу
   `mythgatednd.pp.ua` (той самий, де вже є `/privacy`), щоб додати
   `.well-known/assetlinks.json` і сторінку `/join/:code`. Це вебова робота,
   не зміна коду застосунку (окрім, можливо, додавання другого `<data
android:host="www.mythgatednd.pp.ua">` intent-filter в `AndroidManifest.xml`
   для узгодження з `AppNavigator.tsx`).

     змінюється (edge-to-edge вже був примусовим), зникає лише застарілий

     білд для closed testing, хоча `App.tsx:12-15` вже й так гейтить його
